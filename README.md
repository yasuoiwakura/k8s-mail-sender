# k8s-mail-infra

A small, outbound-only SMTP relay based on [Docker Mailserver (DMS)](https://docker-mailserver.github.io/docker-mailserver/latest/) running on k3s and managed by ArgoCD. It exposes one central SMTP AUTH account that may send as any local part within a set of owned domains, with per-domain DKIM signing and a persistent queue. There is no inbound SMTP, no MX pointing at the relay and no mailbox layer.

## Status

**Phase 2: Kubernetes manifests exist; cluster deployment and tests are still pending.** There is no Docker Compose PoC; the entry point is Kubernetes directly. Secrets are created out-of-band and are not stored in the repository. The manifests have not yet been tested against a real cluster.

## Problem / Motivation

- Apps (Gitea, Authentik, Grafana, Uptime Kuma) and mail clients need to send outbound email.
- Sending as an arbitrary address inside the owned domains should not require an account, alias or mailbox per sender.
- Inbound mail stays with the existing external provider, so no MX changes and no inbound spam/security surface are needed on the relay.
- Delivery must be DKIM-signed per domain and SPF/DMARC compliant, and the queue must survive restarts.

## Solution / Architecture

A single Docker Mailserver pod handles SMTP submission with SMTP AUTH, enforces an envelope-sender domain allowlist, checks the visible `From:` header, rewrites the envelope sender to a reachable bounce address, signs with DKIM and delivers directly to the recipient MX over TCP 25.

```text
Thunderbird / FairEmail / Gitea / Authentik / Grafana / Uptime Kuma
        |
        |  465 implicit TLS  or  587 STARTTLS
        |  SMTP AUTH (one central account)
        v
k3s Service "dms" (LoadBalancer, ONLY 465/587)
        |
        v
Pod "dms" (Docker Mailserver 16.x)
  Postfix submission/submissions
    -> SMTP AUTH via Dovecot SASL
    -> Envelope sender allowlist (check_sender_access)
    -> From: header check (header_checks, defense in depth)
    -> Envelope rewrite to bounces@example.org
    -> OpenDKIM signature with the key table of the From domain
    -> local Postfix queue (PVC)
    -> SMTP client directly to the recipient MX on TCP 25
        |
        v
Internet
```

Port 25 is **not** published externally; the pod may open outbound TCP 25. There is no HTTP ingress for SMTP and Traefik is not needed for SMTP.

## Features

- One central SMTP AUTH account: `smtp@mail.example.com`.
- Send as any local part within `example.org`, `example.net`, `example.com` and `example.info`.
- No sender lists, no per-sender aliases or mailboxes.
- No inbound SMTP and no MX on the relay.
- SMTP submission only on 465 (implicit TLS) and 587 (STARTTLS).
- DKIM per domain, SPF/DMARC compliant delivery.
- Persistent queue and configuration via a PVC.
- Declarative, domain-centric configuration with no secrets in Git.
- Envelope sender rewritten to a reachable bounce address for reliable DSNs.

## Quickstart

Prerequisites:

- k3s cluster with `kubectl` access.
- StorageClass `local-path` (k3s default) or another RWO StorageClass.
- `python3` and `openssl` on the machine that runs the scripts.
- Optional: ArgoCD.
- The DNS entries from [`docs/03-dns.md`](docs/03-dns.md) prepared.

```bash
# Generate ConfigMaps from config/domains.yaml
python scripts/generate.py
python scripts/generate.py --check

# On the Traefik host: extract the TLS certificate from acme.json as the dms-tls Secret
python3 scripts/extract-traefik-cert.py --secret

# In this repository directory
bash scripts/bootstrap-secrets.sh
kubectl apply -f manifests/
```

After that, read the DKIM public keys, create the TXT records and run the SMTP tests from [`docs/05-bootstrap.md`](docs/05-bootstrap.md). `extract-traefik-cert.py` reads `/path/to/traefik/data/acme.json` by default. A self-signed certificate is only possible as a deliberate lab/smoke test: `bash scripts/bootstrap-secrets.sh --self-signed`.

## Configuration

[`config/domains.yaml`](config/domains.yaml) is the single source of truth for the sender domains and central mail settings (hostname, auth account, DKIM selector, bounce/postmaster address, IP protocol). `scripts/generate.py` turns it into the Postfix maps, the DKIM domain list and the two ConfigMaps under `manifests/`.

- **Sender domains:** only domains are configured, never individual sender addresses; the local part is free.
- **Auth account:** `smtp@mail.example.com`, deliberately on the technical hostname domain so no real sender domain becomes local to Postfix.
- **Bounce address:** `bounces@example.org`, delivered through the existing external forwarding; it must not live on a local DMS domain.
- **Secrets:** `dms-account` (the `postfix-accounts.cf` password hash) and `dms-tls` (certificate and key) are created out-of-band, never committed. DKIM private keys are generated by the init container onto the PVC.
- **TLS:** `SSL_TYPE=manual`; the certificate must cover `mx.example.com` and/or `mail.example.com` (a `*.example.com` wildcard covers both). Self-signed is not a production state for SMTP submission.
- **ConfigMap mounts:** files are mounted via `subPath`, so changes are not propagated to a running pod. Roll out after changing configuration (`kubectl rollout restart deployment/dms -n mail`).

See [`docs/05-bootstrap.md`](docs/05-bootstrap.md) and [`docs/06-traefik-tls.md`](docs/06-traefik-tls.md) for the full procedure.

## Limitations / Non-goals

- No inbound SMTP on port 25 and no MX changes.
- No IMAP/POP3 and no mailboxes for end users.
- No spam filter, virus scan or Amavis pipeline.
- No customer domains, per-domain accounts, Sieve or complex routing.
- No HA/multi-replica operation.
- DMS is **not officially** supported on Kubernetes; only community support.
- DMS runs as root and needs capabilities, so PodSecurity `restricted` is not possible.
- NetworkPolicies are not enforced by the default k3s Flannel CNI; the policy is documentation only unless Calico/Cilium is used.
- `local-path` storage is node-local; moving to another node loses queue/config unless shared storage is used.

## Security notes

- Never commit secrets, private keys or passwords. They are created out-of-band and ArgoCD does not manage them in the MVP.
- Do not use a self-signed certificate for production SMTP submission; mail clients validate it like an HTTPS certificate and will not trust it.
- Create the `dms-account` and `dms-tls` Secrets before syncing; ArgoCD does not create them.
- Only ports 465 and 587 are published; port 25 stays closed to the outside and is used outbound only.
- Back up the DKIM private keys. Losing a key while its DNS record remains published causes DKIM failures.
- Keep the SPF, MX and forwarding records of the sender domains intact; this project does not take over inbound mail.
